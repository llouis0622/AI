# 퀴즈 09. MLOps와 시스템

범위: [핸드북 Part 12 · MLOps](/handbook/12-mlops/), [Part 13 · Systems & Hardware](/handbook/13-systems-hardware/).

<QuizProgress prefix="mo" :total="10" />

<Quiz id="mo-01" q="학습-서빙 왜곡(training-serving skew)이란 무엇이며 어떻게 방지하는가?">

**답:** 학습 시점과 서빙 시점의 특징 계산 로직·데이터 분포가 달라져 오프라인 성능과 온라인 성능이 어긋나는 현상이다. 방지: 특징 계산 코드를 학습·서빙이 공유(피처 스토어, 공용 전처리 파이프라인), 서빙 입력을 로깅해 학습 데이터와 비교, 스키마 검증을 자동화한다. → [Part 12 · 03편](/handbook/12-mlops/03-feature-store)

</Quiz>

<Quiz id="mo-02" q="데이터 드리프트와 컨셉 드리프트의 차이를 예와 함께 설명하라.">

**답:** 데이터 드리프트는 입력 분포 $p(x)$의 변화(예: 신규 유저층 유입으로 연령 분포 변화), 컨셉 드리프트는 입력-출력 관계 $p(y|x)$의 변화(예: 팬데믹으로 같은 소비 패턴의 의미가 달라짐)다. 전자는 입력 통계 모니터링으로, 후자는 지연 레이블 기반 성능 모니터링으로 잡으며, 대응은 재학습 트리거다. → [Part 12 · 10편](/handbook/12-mlops/10-monitoring-and-drift)

</Quiz>

<Quiz id="mo-03" q="섀도 배포, 카나리 배포, A/B 테스트의 차이를 말하라.">

**답:** 섀도는 신모델에 실트래픽을 복제해 보내되 응답은 쓰지 않는다 — 무위험 검증. 카나리는 소수 트래픽(예: 5%)만 신모델로 서빙하며 점진 확대 — 위험 최소화 출시. A/B는 트래픽을 무작위 분할해 비즈니스 지표를 통계적으로 비교 — 효과 측정. 순서대로 적용하는 것이 정석이다. → [Part 12 · 11편](/handbook/12-mlops/11-deployment-strategies)

</Quiz>

<Quiz id="mo-04" q="ML 실험의 재현성을 위해 버전 관리해야 할 것 네 가지를 들어라.">

**답:** (1) 코드(git 커밋), (2) 데이터(스냅샷/해시, DVC 등), (3) 환경(의존성 버전, 도커 이미지), (4) 설정과 시드(하이퍼파라미터, 난수 시드). 여기에 학습된 모델 아티팩트와 지표를 실험 추적 도구(MLflow/W&B)로 묶으면 "그 결과가 어떻게 나왔는가"를 되짚을 수 있다. → [Part 12 · 01~02편](/handbook/12-mlops/01-experiment-tracking)

</Quiz>

<Quiz id="mo-05" q="루프라인(roofline) 모델은 무엇을 알려주며, 연산 강도가 낮은 연산의 최적화 방향은?">

**답:** 연산 강도(FLOPs/바이트)에 따라 성능 상한이 메모리 대역폭에 묶이는지(왼쪽) 연산 피크에 묶이는지(오른쪽) 보여주는 모델이다. 연산 강도가 낮은 연산(원소별 연산, 어텐션의 소프트맥스 등)은 FLOPs를 줄여도 소용없고, 메모리 접근을 줄여야 한다 — 커널 퓨전, 타일링, 재계산이 그 수단이다. → [Part 13 · 03편](/handbook/13-systems-hardware/03-roofline-model)

</Quiz>

<Quiz id="mo-06" q="훈련 시 GPU 메모리를 차지하는 네 가지 주요 항목과, 각각을 줄이는 기법을 짝지어라.">

**답:** (1) 모델 파라미터 — 혼합 정밀도, 샤딩(FSDP/ZeRO). (2) 그래디언트 — 샤딩, 그래디언트 누적으로 배치 분할. (3) 옵티마이저 상태(Adam은 파라미터의 2배) — 8비트 옵티마이저, ZeRO. (4) 활성값 — 그래디언트 체크포인팅(재계산), 배치/시퀀스 축소. → [Part 13 · 08편](/handbook/13-systems-hardware/08-memory-accounting)

</Quiz>

<Quiz id="mo-07" q="데이터 병렬, 텐서 병렬, 파이프라인 병렬은 각각 무엇을 나누는가?">

**답:** 데이터 병렬은 배치를 나눈다 — 각 GPU가 전체 모델 복제본으로 다른 데이터를 처리. 텐서 병렬은 한 층의 행렬을 나눈다 — 한 연산을 여러 GPU가 분담(통신 빈번, 노드 내). 파이프라인 병렬은 층을 나눈다 — 모델을 스테이지로 쪼개 마이크로배치를 흘린다(버블 관리 필요). 대형 모델은 셋을 조합한 3D 병렬을 쓴다. → [Part 13 · 06편](/handbook/13-systems-hardware/06-parallelism-strategies)

</Quiz>

<Quiz id="mo-08" q="all-reduce는 무엇을 하는 집합 통신이며, ring all-reduce가 효율적인 이유는?">

**답:** 모든 프로세스가 가진 텐서를 합산(등)해 모두가 같은 결과를 갖게 하는 연산 — 데이터 병렬의 그래디언트 평균이 대표 용례다. ring 방식은 각 노드가 이웃과만 조각을 주고받아 대역폭 사용이 노드 수와 무관하게 최적(2(N-1)/N × 데이터 크기)이라, 중앙 서버 방식의 병목을 없앤다. → [Part 13 · 05편](/handbook/13-systems-hardware/05-collective-communication)

</Quiz>

<Quiz id="mo-09" q="GPU 학습에서 데이터 로딩이 병목인지 판별하는 방법과 해소책을 말하라.">

**답:** GPU 사용률이 주기적으로 떨어지고 프로파일러에서 DataLoader 대기가 보이면 입력 병목이다. 해소: num_workers 증가, pin_memory와 비동기 전송, 디코딩 비용 절감(사전 리사이즈, WebDataset/FFCV 등 효율 포맷), 증강을 GPU로 이동, 프리페치. 스토리지 IOPS 자체가 한계면 로컬 SSD/캐싱으로 옮긴다. → [Part 13 · 07편](/handbook/13-systems-hardware/07-data-loading-and-io)

</Quiz>

<Quiz id="mo-10" q="모델 레지스트리와 승격(promotion) 절차가 필요한 이유를 설명하라.">

**답:** "어느 모델이 지금 프로덕션인가"를 코드처럼 관리하기 위해서다. 레지스트리는 모델 버전·메타데이터·계보를 저장하고, 승격 절차는 스테이징→프로덕션 전환에 자동 평가 게이트(성능 임계치, 회귀 테스트)와 승인을 요구한다. 이것이 없으면 롤백 불가능한 배포, 재현 불가능한 모델이 프로덕션에 남는다. → [Part 12 · 05편](/handbook/12-mlops/05-model-registry)

</Quiz>
